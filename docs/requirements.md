# 海洋鱼类智能化信息管理系统需求说明

## 1. 项目背景

海洋鱼类资料分散，普通用户缺少便捷的查询和识别渠道。部分鱼类资料可能存在错误或未被收录，海洋环境问题和受伤动物也缺少统一的上报、审核与处理流程。

本系统将集中管理常见、珍稀及受保护海洋鱼类的信息，为用户提供学习、查询和智能识别能力，并通过资料纠错、志愿者和救助工单机制，鼓励用户参与海洋生态保护。

> 术语说明：“珍惜鱼类”在正式文档中统一表述为“珍稀鱼类”。

## 2. 项目目标

1. 建立结构化的海洋鱼类信息库。
2. 为用户提供图片和视频鱼类识别能力。
3. 建立受控的鱼类资料纠错和新增流程，防止普通用户直接修改正式数据。
4. 建立环境问题及动物救助事件的上报、审核、接单和反馈流程。
5. 统计系统使用情况，为管理员提供管理依据。

## 3. 用户角色

### 3.1 普通用户

系统的主要使用者，可以查询、识别和上报信息，但不能直接修改正式鱼类资料。

### 3.2 管理员

负责维护系统数据、管理用户、审核各类申请、调度救助工单并查看统计信息。

### 3.3 志愿者

拥有普通用户的基础能力，并可以查看、接受和处理管理员审核通过的救助工单。

## 4. 功能需求

### 4.1 用户与权限

- 游客无需登录即可浏览和搜索鱼类信息。
- 游客只能访问公开页面并执行浏览、搜索等只读操作，不能访问个人中心、识别记录、申请记录和工单处理页面。
- 游客不能使用智能识别、提交申请、上报问题或处理工单；执行这些操作前必须注册并登录。
- 用户可以注册、登录和退出系统。
- 用户可以查看和修改自己的个人资料。
- 不同角色只能访问其权限范围内的功能。
- 管理员可以查询用户、调整用户状态和维护必要的用户信息。
- 普通用户可以提交志愿者申请，申请资料包含真实姓名、手机号、所在地区、擅长领域和申请理由。
- 管理员可以通过或驳回志愿者申请。
- 志愿者申请通过后，用户获得志愿者权限。

### 4.2 鱼类信息管理

- 所有已登录用户都可以浏览和搜索鱼类信息。
- 鱼类信息至少包含中文名、学名、类别、外观特征、生活习性、分布区域、保护级别和图片。
- 管理员可以新增、修改和删除鱼类信息。
- 删除鱼类信息采用逻辑删除：数据仍保留在数据库中，但不再出现在普通查询结果中。
- 普通用户不能直接修改正式鱼类数据。
- 用户发现资料错误或鱼类未收录时，可以提交纠错或新增申请。
- 管理员可以查看申请详情并通过或驳回申请。
- 申请通过后，由管理员确认并更新正式鱼类数据。

### 4.3 智能识别

- 用户可以上传图片进行鱼类识别。
- 图片识别纳入首个正式版本，视频识别在第二次迭代中实现。
- 第二次迭代完成后，用户可以上传视频进行鱼类识别。
- 用户可以选择模型和置信度阈值。
- YOLO 服务返回检测类别、置信度、目标框位置和标注图片，不负责生成鱼类习性等业务资料。
- Spring Boot 根据检测类别查询鱼类信息库，并补充展示鱼类名称、分类、生活习性、栖息地、分布区域和保护级别。
- 原始图片和标注图片保存到文件存储中，数据库只保存文件地址、文件信息和识别结果，不直接保存大文件内容。
- 系统保存用户的识别记录。
- 用户只能查看自己的识别记录。
- 管理员可以查看识别功能的总体使用统计。
- 首个可用版本优先实现图片识别，视频识别在后续迭代中完成。
- 如果模型返回的类别在鱼类信息库中不存在，系统创建一条待管理员处理的资料补全任务；管理员确认资料后再加入正式鱼类信息库。
- 如果没有检测到目标或最高置信度低于阈值，系统提示用户更换清晰图片或调整识别条件，不自动创建正式鱼类资料。
- 文件格式不支持、文件损坏、文件过大、AI 服务不可用、调用超时等异常应返回明确原因。

### 4.4 问题上报与救助工单

- 用户可以上报海洋环境问题或动物救助事件。
- 上报内容至少包含事件类型、标题、问题描述、图片、位置、联系方式和上报时间。
- 事件类型通过下拉框选择，问题描述通过文本框补充。
- 用户可以授权浏览器获取经纬度，也可以手动填写文字地址；拒绝定位权限时不影响手动提交。
- 新提交的上报进入“待审核”状态。
- 管理员可以通过或驳回上报。
- 审核通过的上报转为“待接单”工单，同时生成一条公开救助公告。
- 游客和登录用户都可以浏览公开救助公告，但只有志愿者可以接单。
- 志愿者可以查看并接受待接单工单。
- 一个工单在同一时间只能由一名志愿者负责。
- 志愿者可以提交处理进度和处理结果。
- 处理结果至少包含文字说明、现场图片和提交时间。
- 管理员可以确认工单完成、要求补充处理或退回继续处理。
- 用户可以查看自己提交事项的处理状态。

### 4.5 数据统计

- 管理员可以查看用户数量及角色分布。
- 管理员可以查看图片、视频识别次数。
- 管理员可以查看识别出的主要鱼类类别。
- 管理员可以查看救助工单数量及各状态分布。
- 管理员可以查看志愿者接单和完成情况。

## 5. 核心业务流程

### 5.1 游客与登录用户访问流程

游客浏览和搜索公开鱼类信息或救助公告 → 使用识别、申请、上报或工单功能时进入登录页面 → 登录成功并通过权限校验后执行相应操作。

### 5.2 鱼类资料纠错流程

用户提交申请 → 管理员审核 → 驳回并说明原因，或通过并更新正式鱼类资料 → 用户查看结果。

### 5.3 志愿者申请流程

普通用户提交申请 → 管理员审核 → 驳回并说明原因，或通过并授予志愿者角色。

### 5.4 救助工单流程

用户选择事件类型并填写描述、图片和位置 → 管理员审核 → 审核通过并发布公开公告 → 志愿者接单 → 志愿者处理并反馈 → 管理员确认完成或退回补充。

建议状态如下：

| 状态 | 含义 |
| --- | --- |
| PENDING_REVIEW | 等待管理员审核 |
| REJECTED | 审核未通过 |
| WAITING_ACCEPT | 审核通过，等待志愿者接单 |
| PROCESSING | 志愿者处理中 |
| WAITING_CONFIRM | 已反馈，等待管理员确认 |
| COMPLETED | 工单完成 |
| CANCELLED | 工单取消 |

## 6. 核心功能优先级

### 第一优先级

1. 鱼类信息的增删改查和查询。
2. 图片鱼类识别及识别记录。
3. 救助工单的上报、审核、接单和反馈。

### 第二优先级

1. 用户注册、登录和角色权限。
2. 鱼类资料纠错和新增申请。
3. 志愿者申请与审核。
4. 后台数据统计。

### 后续迭代

1. 视频识别。
2. 摄像头实时识别。
3. AI 鱼类知识分析。
4. 消息通知和地图定位。

## 7. 非功能需求

- 安全性：密码不能明文保存，接口需要进行身份和权限校验。
- 可维护性：后端采用清晰的分层结构，统一响应和异常处理。
- 可靠性：重要业务操作需要校验状态，避免重复接单和越权修改。
- 可追踪性：申请、审核和工单状态变化应保留时间及操作人。
- 易用性：主要页面应提供清晰的成功、失败和加载提示。
- 可部署性：最终支持通过 Docker 启动主要服务。

## 8. 项目边界

第一版不实现在线支付、即时聊天、复杂地图调度和模型在线训练。YOLO 模型训练作为独立学习任务，业务系统优先使用训练好的模型完成推理。

## 9. 求职目标

项目主要用于 Java 后端岗位和 AI 应用开发岗位求职，同时覆盖前后端联调、数据库设计、权限控制、Python AI 服务集成和部署能力。

## 10. 待确认事项

当前初步需求已经确认。后续在数据库设计和接口设计阶段，继续确认字段长度、申请审核细则、工单异常状态和统计口径。
